# 应用入口信息架构收敛（App Entry IA Consolidation）

> 目标：消除「扩展插件 / 微服务界线模糊、app 入口散在三处」的怪味。
> 本文档记录诊断结论、架构判断、实际改动与验证结果，便于逐项复核。

---

## 1. 问题：三个入口，三种切法

改前 app 的入口有三处，而它们**各按不同维度切同一批东西**，互不正交：

| 入口 | 实际切的维度 | 位置 |
|---|---|---|
| 导航栏「应用」 | 是不是**扩展插件**且带 UI | `ExtensionHost.vue` Teleport 到 `#ext-launcher-slot` |
| 头像下拉菜单 | 是不是**管理员功能**（无归属的都往这塞） | `App.vue` 的 `.user-dropdown` |
| 后台管理 `/admin` | 是不是**系统 / 运维** | `Admin.vue` 按 内容 / 系统 / 账号 分组 |

后果是同一类东西（扩展）在两处出现：导航栏里**用**，`/plugins` 里**管**；
而 `/plugins` 又不进 `/admin` 的标签体系——**「管理」这件事本身就有两个入口**。

---

## 2. 根因诊断

### 2.1 "app" 被混用成两个概念（最根本）

- 「用户可消费的**界面**」→ 应用列表
- 「可管理的**运行时单元**」→ 服务管理

扩展两者都是，于是两边都沾；微服务只是后者，所以只存在于后台；
核心功能（上传 / 标签 / 合集 / 帖子 / 文本）只是前者，却**一个都没进应用列表**——
无处安放，只能散落在导航栏左侧和头像菜单里。
**「上传视频」掉进管理项堆里，就是这么发生的。**

### 2.2 头像菜单是杂物抽屉

管理项（管理、扩展管理、凭证保险库）、使用项（上传视频）、个人项（设置、不喜欢）、
信息项（功能指引、反馈中心）并列，不对应任何单一维度。

### 2.3 权限两套判据

菜单到处散落 `v-if="isAdmin"`，路由守卫却看 `meta`。
典型漂移：`/upload` 路由只 `requiresAuth`、后端上传接口本就是 `@auth_required`，
菜单却按 `isAdmin` 藏 → 「路由进得去、菜单看不见」。

## 3. 架构判断

**原则 1：不要把扩展和微服务统一成 "app"——它们不是一层东西。**

```
扩展 Extension = 能力 + UI 的封装，跑在扩展宿主进程里，面向用户
微服务 Service = 独立进程，提供 RPC 能力，面向系统内部
```

一个扩展可以**依赖**多个微服务，微服务永远不直接面向用户。
所以**扩展才是「应用」，微服务是「应用依赖的基础设施」**。
把它们硬并成一个 "app" 列表，正是怪味的来源。

**原则 2：两个正交维度，各留一个权威入口。**

- **用**（用户视角）→ 只有「应用」入口
- **管**（运维视角）→ 只有「管理」入口；扩展与微服务在此并列为
  「可管理的运行时单元」（都有 状态 / 启停 / 配置 / 日志）——这才是它们唯一正确的共同抽象。

**原则 2.1：「应用」的判据是「可独立启动的能力 / 工具」，不是「内容的一个视图」。**

| 类别 | 例子 | 归属 |
|---|---|---|
| 资源类型 / 模式 | 视频、图集、帖子、文本 | 首页模式 tab |
| 浏览维度 | 标签、合集 | 导航栏 |
| 个人集合 | 点赞、收藏、历史、稍后再看、不喜欢 | 导航栏 / 头像菜单 |
| 动作类工具 | 上传 | **应用** |
| 第三方能力 | 扩展 | **应用** |

> 初版曾把前三类一并塞进应用列表，既造成重复入口，又是范畴错误——
> 「帖子」是资源类型，不是一个可独立启动的 app。已收窄（见 §4 Step 3）。

**原则 3：头像菜单只承载「账号」维度**（我是谁 + 我的东西），不承载系统入口。

**原则 4：入口可见性的唯一判据是路由 meta**，与全局守卫同规则。

**原则 5：核心 vs 扩展的判据 = 依赖方向。**

> **被核心依赖的不能拆**（否则核心反向依赖一个可卸载单元）；
> **只依赖外部世界、核心不依赖它的可以拆**（可独立迭代发布、可装卸）。

| 能力 | 依赖方向 | 归属 |
|---|---|---|
| 缓存管理 | 核心服务 → 它 | **核心**（其它服务依赖它） |
| 服务管理（观测/启停 dbox 自身服务） | 它 → 被管服务（含 `dbox-extensions`） | **核心**（工具不能寄宿在它要管的进程里） |
| 系统监控 | 它 → psutil / 机器；核心不依赖它 | **扩展** `extensions/system-monitor` |
| 安装信息 / 路径 | 核心仪表板 → 它 | **核心** `backend/system_info.py` |

注意区分两类「监控」：**服务监控**管的是 dbox 自身进程（含扩展宿主），
必须留核心；**系统监控**只读机器指标、不管任何进程，可以住扩展宿主。
历史上两者曾被一起收进核心，用的理由是前者的，并不适用于后者。

## 4. 改动清单

按逻辑步骤排列（括号内为提交号，实际落地顺序见 §7）。

### Step 1 — 头像菜单瘦身，管理上提为导航栏独立入口 `fe6cd65`

- 头像菜单移除：管理、扩展管理、凭证保险库、上传视频。
- 头像菜单保留：账号信息、设置、功能指引、不喜欢、反馈中心、退出登录。
- 导航栏新增「管理」入口（管理员可见），作为「管理」维度的唯一顶层入口。
- 文件：`src/webui/src/App.vue`

### Step 2 — 扩展管理 / 凭证保险库收编进后台 `1d48a40`

- `Admin.vue` 新增「应用」标签组，与「内容」「系统」「账号」并列：
  - 🧩 扩展管理（原 `/plugins`）
  - 🔑 凭证保险库（原 `/vault`）
- `Plugins.vue` / `Vault.vue` 新增 `embedded` 属性：内嵌时隐藏自身页面标题，
  避免与后台标签页标题重复；工具栏与操作按钮保留。
- 路由：`/plugins` → `/admin?tab=extensions`，`/vault` → `/admin?tab=vault`
  （保留旧链接，且保留 meta 让重定向首趟就受同一套权限校验）。
- 顺带修正：`VALID_ADMIN_TABS` 原先漏了 `trash`，导致从 sessionStorage 恢复
  「回收站」标签会被判非法；后台 `onMounted` 里另存的一份白名单副本改为复用该常量。
- 文件：`src/webui/src/views/Admin.vue`、`Plugins.vue`、`Vault.vue`、`src/webui/src/router/index.ts`

### Step 3 — 应用入口纳入工具（上传） `f6062eb` → `292b68c`

- 应用列表拆为「扩展」「工具」两组（代码为 `toolApps` / `visibleToolApps`）。
- **初版方向过宽**：把「核心功能页面」整体纳入（上传/标签/合集/帖子/文本）。
  其中 帖子、文本 是资源类型（首页模式 tab 已有）、标签、合集 是浏览维度
  （导航栏已有）——既重复入口，又是范畴错误。
- 据此按原则 2.1 收窄：只保留动作类工具 **上传**。
- 应用入口改为对**已登录**用户可用（原仅管理员）：后端上传接口本就是
  `@auth_required`；扩展列表由 `listExtensions` 自行鉴权，非管理员得到空列表，不越权。
- 挂载条件由 `extensions.length` 改为「扩展或工具任一非空」。
- 文件：`src/webui/src/components/ExtensionHost.vue`、`src/webui/src/App.vue`

### Step 4 — 入口可见性统一由路由 meta 推导 `7d14818`

- 新增 `src/webui/src/utils/routeAccess.ts` 的 `canShow(path)`，规则与
  `router/index.ts` 全局守卫逐步对齐（public → 登录 → requiresAdmin 含资源库管理员）。
- 导航栏「管理」入口改用 `canShow('/admin')`；应用列表内置应用按 `canShow` 过滤。
- 此后新增页面只需在路由 meta 声明一次权限，所有入口自动一致。

## 8. 遗留与后续建议

1. **扩展仍为管理员专属**：`/ext/:id` 与 `listExtensions` 均为 admin 权限，
   因此普通登录用户在应用列表只看到「工具」组、看不到扩展。
   若要向普通用户开放扩展，需后端同步放开——属产品决策，本次未擅自改动。
2. **移动端导航栏更挤了**：新增「管理」图标后窄屏需关注换行（已复用
   `.nav-icon-link`，窄屏仅显示图标）。
3. **`/plugins/:id/settings` 仍为独立全屏页**：它是从扩展管理下钻的设置页，
   不是顶层入口，故未收编。
4. **后续可做**：服务管理目前只呈现 NSSM 微服务；扩展并非独立进程（同属
   `dbox-extensions` 宿主服务），若要「运行时单元」视图完全统一，
   可在服务管理里补充扩展宿主与各扩展的运行状态。

## 9. 系统监控：从核心迁为插件（2026-09-08）

仓库：`https://github.com/dzming-git/dbox-ext-system-monitor`（主仓提交 `2f140c7`）。

### 背景：它是被「顺带」收进核心的

核心里原本写着"系统资源监控是平台系统功能，不应寄宿在被它管理的 dbox-extensions 进程"。
这句理由**只对服务监控成立**：服务监控要观测并启停 dbox 自身服务（含扩展宿主），
工具不能寄宿在它要管的进程里。系统监控只**只读**机器指标、不管任何进程，
是被顺带套上了前者的理由。

### 决策：按依赖方向判据迁出（见原则 5）

系统监控只依赖 `psutil` / WMI，核心不依赖它 → 可拆。
核心仪表板原本依赖的 `/info`、`/paths` 本质是**安装信息 / 路径**而非监控指标，
已拆为核心自己的 `backend/system_info.py`（`/api/admin/system-info`、
`/api/admin/system-paths`），避免核心反向依赖一个可卸载单元。

### 迁移范围

| 迁出（→ 插件） | 留在核心 |
|---|---|
| 指标采集与历史（`/metrics/current`、`/metrics/history`、`/stats`） | 服务管理、系统配置、用户管理、资源库、回收站、电源 |
| 机器信息 `/info` | 安装信息 `/api/admin/system-info`、路径 `/api/admin/system-paths` |
| 面板 `ui/panel.html`（原 `core-panels/system-monitor.html`） | 缓存管理（其它服务依赖它，按判据不可拆） |

### 实现要点（改动前务必先读）

- **采样状态跨热重载存活**：插件热重载会重新 import 模块、模块级全局变量全重置，
  但旧采样线程仍在跑 → 新模块历史永远为空，或重复起采样线程（"实例冗余"那类 bug）。
  故共享状态挂在 `sys.modules['ext_system_monitor_shared']`（热重载只摘 `ext_<key>` 包），
  `create_blueprint` 只做「确保采样已启动」。
- 历史落盘到 `host.data_dir`，进程重启不丢 24h 曲线。
- 面板前缀由平台注入 `__EXT_API_PREFIX__`，token 走 `DBOX_TOKEN` 通道。
- 取数失败时顶部显式提示「取数失败：扩展宿主未响应」，不白屏。

### 已知取舍（长期风险）

面板取数走扩展宿主进程；宿主整体不可用时监控不可用，而最需要监控的场景
恰恰可能是"某个扩展把机器搞挂"。已用上述降级提示缓解，但风险本身存在，
且随扩展数量增加而放大。若日后要求"任何情况下都能看机器指标"，
应把采集保留在核心、只把 UI 留在插件（collector / UI 分离）。

### 顺带修正

原先用 `dirname` 链推导安装根**少上了一层**（得到 `<root>/src`），
现统一改用 `backend.paths` 的 `PROJECT_ROOT` / `DATA_DIR` / `USER_CONFIG_DIR`。
