# 触屏键盘弹起/收起窗口错位：修复复盘

> 这个功能前前后后改了 20 多次才稳定。下面老实复盘为什么这么难，以及真正的解法是什么。

## 一、真正的根因（后期才看明白）

这个 webview 有三个反直觉事实，前 20 次方案全部建立在"这些事实不成立"的错误前提上：

1. `visualViewport.scrollTop` / `scrollTo` 是 **NaN**——这个 webview 的 `visualViewport` 根本不支持滚动。所有基于 `scrollTo(0,0)` 的"贴顶部自纠循环"全是空转。
2. `window.scrollY` 永远 **0**——iframe 内没有任何可用的整页滚动 API。
3. 键盘弹起后 `window.innerHeight === visualViewport.height`（即 `ih == vh`），而且两种模式（fit / zoom）**都是 resizes-content 行为**。所以用 `ih − vh` 算键盘高，结果恒为 0，触发不了任何逻辑。

也就是说：键盘高度的"正确来源"既不是滚动量、也不是 `ih−vh`，**只能拿"键盘收起时的全高"减去"键盘弹起时的可视视口高度"**，并且所有"把内容拉上去"的动作都不能用滚动，只能用 `transform: translateY()`（zoom 模式）或收缩 `#app` 高度（fit 模式）。

## 二、为什么改了 20 多次才对

1. **没先测量就动手，靠猜机制。** 前 N 次都在假设"滚动 API 能用""`ih≠vh` 能算出键盘高"。这两点都是错的，于是 20 个方案全建在错误地基上，自然全错。
2. **被"原大小没问题"带偏，编了一套错误理论。** 我曾用 fit/zoom 两模式差异拼出一套"fit 是 resizes-content、zoom 是 resizes-visual"的解释。用户一张截图（放大态 `ih` 也从 598 缩到 361）直接打脸，但这个错误理论没被及时推翻，我又在它的框架里继续打补丁。
3. **症状驱动，不是根因驱动。** 每次只修"当前看到的现象"：上移了→加 transform；收起不回→改判定；又跳→加锚定。没有一次性把"键盘高度到底怎么来、视口锚定在哪、会不会随输入变"想清楚，于是每修一个点又露出下一个点，反复 20 轮。
4. **没把用户给的硬数据当回事。** 用户早就贴出四张截图的 `ih/vh/ot` 原始数据，铁证 `visualViewport` 不可用、`ih==vh`。我后期才真正读进去并据此重写。如果第一次就严格按数据建模，几步就能到正解。
5. **过度工程引入新 bug。** 为了"贴住"，加了一堆每帧 `requestAnimationFrame` 重算和 `scrollTo(0,0)` 自纠循环，结果这些本身造成跳动，又得再修——等于用错误的手段修错误的前提。
6. **验证回路慢。** 每次都要用户在真机硬刷新 + 截图反馈，单轮成本高，所以在错误方向上迭代了很多次才被数据拉回来。

## 三、最终稳定的解法（本质其实很简单）

- 以"键盘收起时全高 `fullH`"与"键盘弹起时可视视口高 `visH`"之差 `kbH = fullH − visH > 20` 作为**唯一**的键盘弹起/收起判定，不依赖 `blur`（收起时 `#kb` 焦点常残留，会卡住窗口）。
- zoom 模式：`#app` 保持全高，仅用 `transform: translateY(-kbH)` 把整块顶到键盘上方，**不碰 `.view` 内部滚动**，用户当前视角完全保留。
- fit 模式：收缩 `#app` 高度到 `fullH − kbH`，resizes-content 天然把整块落到键盘之上。
- 上移量 `kbLiftH` 在键盘弹出后**前 400ms 取最大值**（覆盖候选栏早期出现），**400ms 后锁定为恒定值**，整个聚焦期间不再随 `visH` 变化重算 → 打字不再二次上移。
- `fullH` 仅在 `fullH − visH <= 20`（键盘真正收起）时更新，避免输入法临时失焦把全高误写成键盘态小值。
- 修掉一处隐藏的 `ReferenceError`：文件别处的 resize 监听仍调用已删除的 `liftForKb`，会抛错中断整段脚本。

## 四、仍留作独立问题

输入文字后，输入法**候选词栏**偶尔仍会再引起一次轻微上移（候选栏出现晚于 400ms 锁定窗口时）。归类为独立待办，后续可把锁定延时调到 600ms 或在候选栏出现后再补一次锁定。

## 五、给以后的教训

1. **先测后写**：webview / 小程序环境不要假设标准浏览器 API 全可用，先用数据确认 `scrollY`、`visualViewport`、各高度字段的真实取值。
2. **截图里的原始数据比自己的理论更可信**，一旦数据与假设冲突，先推翻假设。
3. **用最少假设解释一个现象**，别为单个症状叠补丁；一次性把"高度怎么来、锚定在哪、何时变"想清楚。
4. **UTF-8 提交**：Windows 下中文提交信息务必落 UTF-8 文件用 `git commit -F`，别让终端 GBK 把信息写乱。
